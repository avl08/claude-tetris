# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Classic Tetris implemented in vanilla JavaScript with HTML5 Canvas and CSS. No dependencies, no build tools, no package.json — `index.html`, `style.css`, and seven scripts (`audio.js`, `effects.js`, `powerups.js`, `scores.js`, `skins.js`, `pausemenu.js`, `game.js`, loaded in that order).

## Running

There is no build/test/lint tooling in this repo. To run the game, open `index.html` directly in a browser, or serve it locally (needed if the browser blocks local file access):

```bash
python3 -m http.server 8000
# or
npx serve .
```

Then visit `http://localhost:8000`. To verify a change, open the page in a browser and play — there are no automated tests.

## Architecture

Core game logic lives in `game.js` (single file, no modules). The power-up system is split into three sibling scripts that `game.js` talks to only through a narrow context object — see below. Key pieces:

- **Board model**: `board` is a `ROWS × COLS` matrix. Cell values: `0` empty, `1–8` a piece color (including the 3×3 "nut"), `9` a **comodín** (wildcard, created by the Tinte power-up), `100 + n` a power-up cell (transient — it only exists between `merge()` and its own activation inside the same `lockPiece()` call, and never survives to a normal render).
- **Pieces**: `PIECES` defines the 7 classic tetrominoes plus an 8th challenge piece — a 3×3 "nut" ring (`[[8,8,8],[8,0,8],[8,8,8]]`) with an unfillable hollow center — as square matrices. `randomPiece` picks uniformly among all of them (`PIECES.length - 1`, so the range stays correct if `PIECES` grows). `rotateCW` rotates via transpose + row-reverse (a no-op for the symmetric nut, and for the 1×1 power-up pieces). `tryRotate` applies `rotateCW` then attempts wall kicks (`[0, -1, 1, -2, 2]` column offsets) until a non-colliding position is found.
- **Collision**: `collide(shape, ox, oy)` checks bounds and overlap against `board`; used for movement, rotation, ghost-piece projection, and drop-lock detection.
- **Game loop**: `loop(ts)` runs via `requestAnimationFrame`, with `dt` clamped to 100ms. Skips the drop/freeze logic while `paused` or `gameOver`, but always updates `Effects` and redraws — so a power-up's visual effect (e.g. a bomb's explosion) keeps animating for a few frames after pause or game over instead of freezing mid-animation. `dropAccum` accumulates against `dropInterval`; when exceeded, the piece drops one row or locks (`lockPiece`) if blocked. While `freezeRemaining > 0` (see Congelar below), dropping is suspended and `dropAccum` is held at 0 instead.
- **Locking a piece**: `lockPiece` → `merge` (writes piece into `board`) → `PowerUpSpawner.onPiecePlaced()` → activates the piece's power-up if it has one (`activatePowerUp`) → `clearLines` (removes clearable rows, shifts down, updates score/level/speed) → `registerCombo` (combo bonus for consecutive clearing locks) → `spawn` (promotes `next` to `current`, generates new `next` via `nextPiece()`, checks game-over via immediate collision).
- **Line clearing**: a row is clearable when `huecos <= comodines` (`isRowClearable`), i.e. every gap in that row is covered by a wildcard — the classic "no gaps at all" rule is just the `comodines = 0` case. `clearLines()` returns `{ cleared, comodines }`; `applyLinesCleared(count, comodines)` does the scoring (with a comodín bonus) and level-up math shared with `clearRow`.
- **Scoring/leveling**: `LINE_SCORES = [0,100,300,500,800]` × `level`; hard drop adds 2 pts/row, soft drop 1 pt/row. Level increases every 10 lines; `dropInterval = max(100, 1000 - (level-1)*90)`. Consecutive locks that clear at least one line build a `combo`; from the second consecutive clear onward it adds `50 × (combo-1) × level`.
- **Rendering**: `draw()` clears and redraws the grid, locked board, ghost piece (`ghostY()` projects current piece straight down, drawn at `globalAlpha 0.2`), the current piece, and finally `Effects.draw()` (with a screen-shake offset from `Effects.getShakeOffset()`) — all skipped for the current/ghost piece once `gameOver` is true. `drawBlock`/`resolveCell` decode a cell value into a fill color and an optional glyph (comodín, or a power-up's own glyph); a falling power-up piece passes its live instance through so per-instance state (e.g. which color the Tinte picked) renders correctly. `resolveCell` routes normal piece colors (`1-8`) through `Skins.colorFor(v)` (see Visual skins below) — the comodín and power-up branches are untouched. `drawBlock` keeps its exact signature and all four call sites (board, ghost, current piece, NEXT preview); it delegates the block-body painting to `Skins.paint(context, x, y, size, fill, highlight)` and still draws the glyph text itself, generically for every skin. `drawNext()` renders the preview canvas, centering 1×1 power-up pieces by bounding box instead of the normal 4×4 grid offset.
- **Input**: single `keydown` listener dispatches arrow keys/X/Space/P/Escape to movement, rotation, soft/hard drop, and pause; unaffected by Congelar (only automatic dropping is suspended). While the help modal is open (`isHelpOpen()`), the listener only handles `Escape`. `KeyP`/`Escape` otherwise always call `togglePause()` unconditionally (checked before the `paused || gameOver` early-return) — since `paused` is true exactly while the pause menu is open, this single check both opens the menu and (pressed again) closes it, with no separate `PauseMenu.isOpen()` branch needed. The listener's very first check, `if (e.target instanceof HTMLButtonElement) return;`, is why every pause-menu button calls `.blur()` on click before invoking its callback — otherwise a focused button would eat all keyboard input after the menu closes.
- **Pause menu** (`pausemenu.js`, `PauseMenu` object): `div#pause-menu.overlay.hidden` in `index.html`, sibling of `#overlay`/`#help-modal` (placed between them so the help modal — opened via its "Ver controles" button — stacks visually on top of it). Decoupled the same way as the power-up system: `game.js` calls `PauseMenu.init({ onResume, onRestart, onControls })` once at startup and `PauseMenu.open()/close()/isOpen()/getStartLevel()` from `togglePause()`, `init()`, and the keydown listener; no game state is touched from `pausemenu.js` directly. `togglePause()` (game.js) now opens/closes this menu instead of writing "PAUSA" into `#overlay` — `#overlay` is game-over-only. Opening the menu calls `stopRepeat()` (as the old pause path did) so a held touch button doesn't keep firing underneath it; touch actions stay blocked automatically because they're all self-guarded by `if (paused || gameOver) return`, and `togglePause()` still sets `paused = true`. The "Ver controles" button calls `openHelp()` directly — since `paused` is already `true`, `openHelp()`'s own bookkeeping no-ops and closing help just reveals the still-open pause menu underneath. **Nivel inicial**: a 1–10 number input, persisted in `localStorage` under `tetris-start-level` (`try/catch`-wrapped, same convention as `tetris-theme`/`tetris-mode`) and read once by `PauseMenu.getStartLevel()`. `game.js` snapshots it into its own `startLevel` variable inside `init()` (seeding both `level` and `dropInterval`) rather than re-reading `PauseMenu.getStartLevel()` live elsewhere — `level` is recomputed on every line clear (`applyLinesCleared()`: `level = startLevel + Math.floor(lines / 10)`), so a live read there would let changing the selector mid-pause retroactively alter the level of the game already in progress.
- **Game mode**: `gameMode` (`'classic' | 'full'`, persisted in `localStorage` under `tetris-mode`) is set via `setMode()`, which flips `PowerUpSpawner.config.enabled` and — unless called with `{ restart: false }` during startup — calls `init()`. In `classic` mode the spawner's `enabled` check short-circuits before the `forcedNext` check, so even `window.__spawnPowerUp(...)` is a no-op.
- **Help modal**: `openHelp()`/`closeHelp()` toggle `#help-modal`. Opening it pauses the game only if it wasn't already paused/over (tracked via `helpCausedPause`), so closing it only resumes when the modal itself caused the pause — a pre-existing manual pause or game-over state is left untouched.
- **Start screen / local high scores (`scores.js`)**: the game no longer auto-`init()`s. `gameOver` starts `true` (set at declaration, before any `init()` call) so every input guard (`moveLeft`/`rotate`/etc., each self-guarded by `if (paused || gameOver) return`, including the touch buttons that call them directly) rejects input while `#start-screen` — an `.overlay` shown by default, not `.hidden` — is up. Its **Jugar** button hides `#start-screen` and calls `init()`; **Borrar récords** clears storage after a `confirm()` and re-renders the table in place. `scores.js` exposes a standalone `Scores` object (no globals touched directly, same pattern as `Sfx`/`Effects`): `getScores()`/`addScore()`/`qualifies()` manage the top-5 array under `localStorage['tetris-highscores']` (the codebase's first JSON-structured value — `getScores`/`addScore` defensively validate shape and wrap read/write in `try/catch`, falling back to `[]`), while `getBestCombo()`/`updateBestCombo()` and `getMaxLines()`/`updateMaxLines()` track two running-maximum integers in their own plain-string keys (`tetris-best-combo`, `tetris-max-lines`), consistent with the rest of the codebase's non-JSON keys. `renderTableHTML()` builds the shared markup used by both the start screen and the game-over overlay. `registerCombo()` (~line 205) calls `Scores.updateBestCombo(combo)` at the point `combo` is incremented — not later, since the very next non-clearing lock resets `combo` to 0 in the `else` branch — and also tracks a per-run `runBestCombo` (reset in `init()`) that becomes the `combo` field of a saved score entry. `endGame()` calls `Scores.updateMaxLines(lines)` (safe to read `lines` there — only `init()` resets it) and renders the top-5 table plus bests into `#overlay-extra` inside the existing `#overlay`; if the run's score `Scores.qualifies()`, a name `<input>` + save button appear, and saving calls `Scores.addScore()` and re-renders with the new row highlighted (`.score-row--new`). The keydown listener's early-bail (~line 680) was widened from only `HTMLButtonElement` to also exempt `HTMLInputElement`/`isContentEditable`, so typing a name doesn't trigger `KeyP` (pause) or `Space` (hard drop). `#overlay`/`#overlay-extra` are game-over-only — pausing goes through `PauseMenu` (see above) instead.

Tunable constants at the top of `game.js`: `COLS`, `ROWS`, `BLOCK`, `COLORS`, `LINE_SCORES`, initial `dropInterval`. If `COLS`/`ROWS`/`BLOCK` change, update the `<canvas id="board">` `width`/`height` in `index.html` to match (`COLS × BLOCK`, `ROWS × BLOCK`).

### Power-up system (`powerups.js`, `effects.js`, `audio.js`)

Decoupled from the engine: no power-up class touches `game.js` globals directly. `game.js` builds a single `powerUpContext` (alongside the board primitives it wraps: `getCell`, `setCell`, `clearCell`, `isInside`, `forEachCell`, `clearRow`, `clearColumn`, `applyGravity`, `addScore`, `getLevel`, `colorHex`, `freeze`, plus `effects`/`sfx`), and every power-up interacts with the game only through it.

- **`PowerUp` (base class) + `PowerUpRegistry`**: each subclass registers with `PowerUpRegistry.register(cls)`, which assigns its cell code (`100 + registration index`) and stores it as `cls.code`. **Registration order fixes the codes — new entries always go at the end.** Adding a power-up means: write the class (its `static id/label/color/glyph/weight/description` plus an `activate(x, y)` method) and register it at the end of the list in `powerups.js`; nothing else changes.
- **The five pieces**: `Bomb` (destroys a 3×3 area, then gravity, `ExplosionEffect` + screen shake + `sfx('explosion')`), `LightningRow`/`LightningCol` (direction fixed when the piece spawns — shown as `↔`/`↕` in the NEXT preview; the row variant uses `ctx.clearRow(y)`, which counts as a real line clear with its combo; the column variant uses `ctx.clearColumn(x)` and does not count as a line), `Dye` (picks a color present on the board at construction time, turns it into comodín/wildcard `9` cells), `GravityPowerUp` (compacts the whole board), `Freeze` (`ctx.freeze(5000)`).
- **`PowerUpSpawner`**: counts pieces placed (`onPiecePlaced`) and lines cleared (`onLinesCleared`) to decide when to offer a power-up, per `POWERUP_CONFIG` (`minGap`, `chance`, `maxGap`, `weights`). `game.js`'s `nextPiece()` asks it on every spawn; if it declines, `randomPiece()` runs as usual. `window.__spawnPowerUp(id)` forces the next power-up from the console (ids: `bomb`, `lightningRow`, `lightningCol`, `dye`, `gravity`, `freeze`) — handy for testing since there's no automated test suite.
- **`effects.js`**: visual effects with `update(dt)`/`draw(context, BLOCK)` deliberately split apart, so `setTheme()` can redraw without advancing animation time. Every hardcoded color literal was extracted into a module-level `effectsPalette` object (`ring`, `particle`, `beam`, `flash`, `streak`, `freezeTint`, `freezeText`, defaulting to the original retro values); each effect's `draw()` reads from it instead of a literal, and `Effects.setPalette(partial)` (in the IIFE's returned API) merges new values in — called from `setSkin()` on every skin change.
- **`audio.js`**: WebAudio-synthesized SFX (no audio files), with the `AudioContext` created lazily on the user's first gesture; mute state persisted in `localStorage`.

### Visual skins (`skins.js`)

A second, orthogonal axis to the dark/light theme above: `data-skin` attribute on `<html>`, persisted under `tetris-skin` (the theme's `data-theme`/`tetris-theme`/`setTheme()` are untouched and keep working independently — combining the two never crashes, e.g. neon skin + light theme, though `[data-skin="neon"|"pastel"|"pixel"]` in `style.css` share specificity with `[data-theme="light"]` and are declared later, so a skin's own chrome variables — `--bg`, `--board-bg`, `--accent`, etc. — win over the theme's for that skin's "complete look", by design per the original feature request). Bootstrapped once in `game.js` next to the `setTheme(...)` call, reading the persisted value and defaulting to `'retro'`.

- **`SKIN_TABLE`** (in `skins.js`) has four entries — `retro`, `neon`, `pastel`, `pixel` — each with a `colors` array (same shape as `game.js`'s `COLORS`), a `paint(ctx, x, y, size, fill, highlight)` block-body painting strategy, and an `effects` sub-palette consumed by `Effects.setPalette()`. `skins.js` loads before `game.js`, so `retro`'s `colors` starts as its own literal copy of the original palette; `game.js` immediately overwrites it with `Skins.get('retro').colors = COLORS` right after declaring `COLORS`, so the two never drift apart — `COLORS` stays the single source of truth for the retro palette.
- **`Skins` (IIFE)** exposes `setActive(id)`/`getActive()`/`get(id)`/`colorFor(index)`/`paint(...)`/`ORDER`. `game.js` only calls through this API — `resolveCell()` routes the `1-8` color branch through `Skins.colorFor(v)`, and `colorHex()` (used by the Tinte power-up to know what color it's about to convert) calls `Skins.colorFor(index)` too. The comodín (`v === 9`) and power-up (`v >= 100`) branches in `resolveCell` are unaffected.
- **Paint strategies**: `paintFlat` (retro — the original flat fill + highlight strip), `paintNeon` (glow via `ctx.shadowBlur`/`shadowColor`, wrapped in `save()`/`restore()` so the glow can never leak into the grid or later draw calls), `paintPastel` (rounded corners via `ctx.roundRect` with a manual arc-based fallback, inset slightly, highlight clipped to the rounded path), `paintPixel` (flat fill plus a cheap 3×3 checkerboard + outline stroke, a handful of extra `fillRect`/`strokeRect` calls per block).
- **`setSkin(skin)`** in `game.js` (modeled directly on `setTheme()`): normalizes via `Skins.setActive`, sets `document.documentElement.dataset.skin`, persists to `localStorage` (try/catch), updates `aria-pressed` on the four `.skin-btn` buttons, calls `Effects.setPalette(active.effects)`, re-reads `themeColors` via `readThemeColors()` (skin CSS blocks also override `--grid-line`/`--block-highlight`/`--comodin`), then redraws guarded by `if (current) draw(); if (next) drawNext();` — needed because `setSkin` runs once at bootstrap before `init()`.
- **CSS**: `style.css` adds `[data-skin="neon"|"pastel"|"pixel"]` blocks overriding the same custom properties the theme blocks use (`--bg`, `--board-bg`, `--accent`, etc. — plus `--grid-line`/`--block-highlight`/`--comodin`), and `[data-skin="pixel"] #board, [data-skin="pixel"] #next-canvas { image-rendering: pixelated }` so the pixel texture doesn't blur when the canvas is CSS-scaled (mobile `aspect-ratio`/shrink at ≤600px — the backing store stays the JS-declared size).
